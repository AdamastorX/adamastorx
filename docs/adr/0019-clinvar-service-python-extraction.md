# 0019. Extract ClinVar into its own Python service; Python approved for bioinformatics-domain components

Status: Accepted

## Context

ADR 0018 split ClinVar responsibilities across the existing Java components: `workers` would ingest (download, tabix-index, write `clinvar_release`/`clinvar_variant_index` rows), `api` would look up (query the tabix file directly via htsjdk, query the same Postgres tables directly via JPA, cache-aside in Redis) and consume an invalidation event by re-reading both old and new tabix files itself to compute the diff.

Deploying this for real (platform#37) surfaced the same root cause twice in a row, not two unrelated bugs:

- **The shared tabix-indexed VCF file**: written by `workers` onto a PVC in the `workers` namespace, needed for read by `api` in the `api` namespace. PersistentVolumeClaims are namespace-scoped in Kubernetes — there is no mechanism to mount one PVC across namespaces without real network-attached storage (NFS or equivalent), which this project doesn't run. `api`'s pod failed to schedule at all: `persistentvolumeclaim "workers-refdata" not found`.
- **The Postgres credential**: `clinvar_release`/`clinvar_variant_index` live in the same Postgres instance as `work_items`, whose generated password Secret lives in `api`'s namespace (ADR 0012 — Postgres was deliberately placed there because Secrets are equally namespace-scoped and can't cross namespaces either). The moment `workers` also needed direct JDBC access to those tables, it hit the identical wall: no `postgresql` Secret in the `workers` namespace.

Both failures are the same class of mistake: ADR 0018 assumed data written by one component in one namespace could simply be read by another component in a different namespace, without an explicit mechanism to cross that boundary. Patching each symptom separately (duplicate the Secret, add a second PVC, etc.) would still leave a third instance of the same bug waiting for the next ClinVar-adjacent feature.

Separately, and independently of the namespace bug: `api`'s ClinVar code used `htsjdk` for VCF/tabix access — a real, functioning, but minority choice in the field. `pysam` (a thin wrapper over the same underlying `htslib` C library) is the tool practitioners in this domain actually reach for; it's also what the project owner, who holds a bioinformatics degree, is more fluent in than JVM-side genomics tooling. A later cross-domain review of this project's bioinformatics-relevance had already flagged htsjdk as unusual; this ADR is the point where that observation becomes a decision rather than a footnote.

## Decision

**Extract all ClinVar/gnomAD-specific logic into a new, standalone component, `clinvar-service`, written in Python.** This is the project's first non-JVM component. The language choice is scoped narrowly, not a wholesale platform migration:

> **Bioinformatics-domain logic (parsing/querying genomic file formats, running bioinformatics tools, anything where the Python ecosystem — `pysam`, `biopython`, and eventually workflow-adjacent tooling for the reserved M6 milestone — is genuinely the stronger fit) is built in Python. Everything else (the existing `gateway`/`api`/`workers` request/response and messaging shape, generic infrastructure code) stays in whatever language already fits it — Java/Spring today, not Python by default.** A future component doesn't get written in Python just because this one is; it earns that choice the same way this one did, with a stated reason.

**`clinvar-service` owns, exclusively:**
- ClinVar GRCh38 ingestion: scheduled download, `pysam`-based tabix indexing, checksum validation of NCBI's published `.tbi` (same policy as before, reimplemented in Python).
- The `clinvar_release` / `clinvar_variant_index` Postgres tables — **on their own, dedicated Postgres instance**, not the same instance `work_items` lives in. Same reasoning ADR 0012 already used for placing Postgres in `api`'s own namespace: a single consumer, a generated credential that can't cross namespaces. Sharing `api`'s Postgres instance across a namespace boundary would just be the exact bug this ADR exists to stop making. Two small Postgres instances on a dev cluster is a cheap, boring, correct answer; a cross-namespace secret-sync mechanism is not.
- The internal HTTP lookup endpoint (`GET /internal/clinvar/lookup`, coordinates or rsID in, clinical significance + optional gnomAD frequency + release id out) — reads its own local tabix files and its own local Postgres, both in the same namespace, no cross-namespace access of any kind.
- Release-diff computation on ingestion: when a new release lands, `clinvar-service` — which holds both the old and new tabix files locally — computes exactly which cached keys' classification changed, and publishes that list (not just a release identifier) on the existing `clinvar.ingestion.completed`-shaped Kafka event. This is the fix for the second half of ADR 0018's original mistake: `api` should never need to re-read a tabix file itself just to know what to invalidate.
- Its own PVC, own namespace (`clinvar`), own NetworkPolicy egress rule to NCBI (same pattern `workers`' now-reverted rule established) — single consumer this time, genuinely, so none of the namespace problems above recur.

**`workers` reverts to its original scope**: the M2 `work-items` Kafka consumer only. All ClinVar ingestion code added under services#25 is removed from it, not left dormant. Its PVC, its Postgres env vars, its ClinVar-specific env vars are all removed in the same change — this component should not carry infrastructure for a responsibility it no longer has.

**`api` keeps**: the public `/variants/lookup` endpoint, Redis cache-aside (unchanged — `WorkItemCacheService`'s established fail-open pattern, just fronting a different upstream now), and the Kafka consumer that reacts to `clinvar-service`'s invalidation event — but that consumer now just deletes the specific Redis keys the event names, exactly the generic, language-agnostic infrastructure work the "components that don't need Python stay in whatever fits" principle describes. `api` loses: the `htsjdk` dependency, direct Postgres access to `clinvar_release`/`clinvar_variant_index` (and the Flyway migration for those tables moves to being `clinvar-service`'s own migration, not `api`'s), and its PVC mount. `api` calls `clinvar-service` over HTTP (`CLINVAR_SERVICE_URL`, Service DNS `clinvar-service.clinvar.svc.cluster.local`) exactly the way `gateway` already calls `api` (ADR 0010) — the same pattern this project already trusts, applied to a new internal boundary instead of invented fresh.

**Stack for `clinvar-service`**: FastAPI (typed, async-friendly, has mature OpenTelemetry instrumentation — matters for keeping this project's cross-correlated tracing story intact across the new language boundary), `pysam` for VCF/tabix, a plain Postgres driver (`psycopg`) rather than a heavier ORM — this service's data access is narrow (two tables, simple queries) and doesn't need JPA-equivalent machinery. A Python Kafka client (`confluent-kafka`, the same librdkafka-backed client most production Python Kafka consumers use) for the ingestion-completed/invalidation event.

## Consequences

- This project is polyglot for the first time. That's a real, deliberate increase in operational surface — a second Docker base image, a second dependency-scanning path in CI (Trivy's filesystem/Python-dependency scan mode, not just the existing JVM image scan), a second OpenTelemetry SDK to keep instrumented consistently with the existing Java services' tracing behavior. Accepted because the alternative (forcing bioinformatics-domain code to stay in Java for stack uniformity) was already producing real friction (the minority-tool htsjdk choice, awkward Testcontainers-in-JVM patterns for VCF fixtures) that a Python-native toolchain doesn't have.
- Two Postgres instances now exist on this single dev cluster (`api`'s `work_items` instance, `clinvar-service`'s own). More moving parts, but each is boring, small, and matches an already-established pattern rather than inventing a new one (a secret-sync tool, a shared-database-with-cross-namespace-access hack) to avoid it.
- `workers` (the Kafka consumer) and `clinvar-service` (the Python HTTP+ingestion service) are both, confusingly, "the thing that isn't `api`" — worth being explicit in naming and documentation that they are unrelated components with unrelated responsibilities that happen to have landed in the same milestone, not two halves of one system.
- `services#25`/`#26`'s original Java implementations (already merged) are being removed, not iterated on — this ADR supersedes their approach entirely rather than patching it. The lesson (namespace-scoped resources can't cross namespaces, checked twice now: Secrets in ADR 0012, PVCs here) is retained in `docs/SESSION_STATE.md`, not just in this ADR's history.
- Backlog #30 (the reserved future M6 milestone, real batch/alignment pipeline) gets more concrete now that this project has a real Python/bioinformatics-tooling foothold (`clinvar-service`) to extend from, rather than starting that language decision from zero when M6 begins.
